# Ren'Py 路线设计速查（route-map 双向闭环）

> 本文件为 **v0.3**——〇~五章经与项目作者逐章协作确认（2026-08-17），可直接使用。
> 协作原则：以状态机为唯一底层模型，叙事概念皆为表达层。

## 〇、基础模型：剧情分支的本质是状态机（已确认）

> 所有剧情分支设计——flag、好感度、路线锁定、多周目、事件时序——本质只有一个：**状态机**。
> 这些叙事概念是"人的思维范式"（表达层），落实到编程一定是状态机；部分高频结构 Ren'Py 提供了独立语句（如 `menu`）。

### 0.1 状态机四要素与 Ren'Py 映射

| 状态机概念 | 定义 | Ren'Py 实现 |
|---|---|---|
| **状态** | 游戏执行到某时刻所处的位置 | label / say 交互点 / menu / pause / 场景 |
| **转移** | 从当前状态到下一状态的过程 | 顺序执行、`jump`、`call`+`return`、menu 选项、if 分支 |
| **守卫** | 转移能否发生的条件 | if/elif 表达式、menu 选项的 when 条件、数值/flag 判断 |
| **事件** | 用户触发转移的动作 | 点击推进（dismiss）、选择 menu 项、按键 |

### 0.2 叙事范式 = 状态机的表达层

| 叙事说法 | 状态机表达 |
|---|---|
| "flag 解锁剧情" | 守卫：`if flag_a:` 才可见某转移 |
| "好感度达到 70 进线" | 守卫：`if affection >= 70:` |
| "路线锁定" | 进入角色线状态后，其他线的转移守卫恒 false |
| "多周目继承" | 初始状态的变量带持久值（persistent/存档） |
| "死路" | 某状态无出转移 |
| "循环/回环" | 转移回到前驱状态 |
| "不可达" | 从初始状态无路径到达的状态 |

### 0.3 menu = 状态机的语法糖

`menu:` 是 Ren'Py 对"多选项交互状态"高频模式的封装——本质是：一个状态，多条带守卫的事件转移（每个选项一条），等待用户选择事件触发。

### 0.4 对数据结构的意义

route-map.json 不需要单独的"flag/好感度/路线"类别——**全部表达为守卫（guard 表达式）+ 变量（variables）**。叙事层的概念是给人看的注释/说明，机器层只有状态机。

### 0.5 双向转换的推论

- 设计文档 → 状态机：把叙事描述翻译成"状态+转移+守卫"
- 状态机 → 代码：按映射表生成 Ren'Py 语法
- 代码 → 状态机：静态分析提取
- **本 skill 的核心价值 = 这个映射表（叙事 ↔ 状态机 ↔ 语法）的准确性**

## 一、分支分类（协作确认，2026-08-17）

> 剧情分支的叙事分类，全部落实到状态机（状态+转移+守卫）。以下为项目作者确认的行业真实用法。

### 1.1 六类分支的真实形态

| # | 分类 | 真实用法（作者确认） | 状态机表达 |
|---|---|---|---|
| 1 | **线性 + 单选分叉** | 最常见的范式。单线剧情用无关紧要的分支塞玩笑话；也存在**分支影响隐藏数值**的用法 | menu 多选项转移；选项可附带变量写入（隐藏数值） |
| 2 | **flag 条件分支** | **放后期**，用**前期影响的数值**，让玩家在"不选择"的情况下也出现路线分叉或文本差别 | 后期状态的守卫引用前期写入的变量（延迟影响） |
| 3 | **好感度/数值阈值** | 带**重复流程养成**的游戏常见；与 1、2 组合使用 | 守卫：`if affection >= N:` |
| 4 | **路线锁定（个人线）** | 非常常见。**共通线**含不同角色事件 → 进入特定分支/数值达标 → 进**个人线**，**本质是关闭部分分支**。个人线从共通线**渐进过渡**（部分分支关闭），进入后**完全分支或几乎不分均可** | 共通线状态多条出转移 → 过渡状态部分转移守卫失效 → 个人线状态（分支度不定） |
| 5 | **多周目/继承** | 常见。需**跨单个存档存在**的隐藏 flag（persistent） | 初始状态带 persistent 变量（跨会话初始条件） |
| 6 | **事件时序触发** | **就是 3**，不单独成类 | —（合并入数值阈值） |

### 1.2 关键修正点（区别于想当然的理解）

1. **flag 不是即时判断**：分类 2 是"前期埋值 → 后期自动分叉"，不是当前选择即时决定
2. **个人线 = 关闭分支**：不是新增剧情，是其他角色线的转移守卫失效；过渡是渐进的
3. **个人线分支度不定**：一进去就完全分支、或几乎完全不分，都是合法形态
4. **多周目 = persistent 跨存档**：状态机的初始状态带持久变量

### 1.3 分支汇聚

- 汇聚**和**独立结局都会出现
- 也有在**章节处汇聚，但后续还是分开的**——汇聚是**中间节点**，不是终结
- 状态机表达：多个转移指向同一状态，但该状态仍有多个出转移（可再分叉）

### 1.4 死路与循环

| 类型 | 态度 |
|---|---|
| **彻底的死路**（无任何出转移） | ❌ 一定不能存在（设计缺陷） |
| **彻底的循环**（无限回环无出口） | ❌ 一定不能存在 |
| **带隐含脱出条件的死路/循环** | ✅ 合法设计手法（如循环内 `if count >= N: jump exit`） |

**对分析器的意义**：判定"死路/循环"不能只看结构（有无出转移），要结合**守卫的可满足性**——看似死路的状态可能有隐藏变量转移，看似循环的转移可能有隐含脱出条件。**两阶段判定都做**：①结构判定（有无出转移）→ ②守卫可满足性分析 → 输出"真死路 / 条件循环 / 正常"分类。

### 1.5 随机性（协作补充，第七要素）

> 随机分支：用生成随机数实现，通过设定条件控制概率分布。

| 状态机表达 | Ren'Py 实现 |
|---|---|
| 随机转移带概率 | `if renpy.random.random() < 0.3:` → 30% 分支 |
| 概率受变量控制 | `if renpy.random.random() < drop_rate:`（如好感越高越易触发） |
| 多分支间分配概率 | `renpy.random.choice([...])` / 多路 `if random < 阈值` |

**三种典型用法**（作者确认）：① 到某点固定概率触发分支 ② 数值越高越容易触发（概率受变量）③ 几个分支间分配概率。

**随机可见性**：不预设——看作者意图：
- 明示随机（玩法机制）→ 状态机标注 `random: true, probability: N`
- 隐藏随机（剧情假随机）→ 同样记录，标注 `player_visible: false`

### 1.5b 剧情锁（协作补充）

> **剧情锁**：本质是个变量，但看的是**存档内有没有进入过相关分支或看过特定 label**——**跨存档**（persistent）。

- 状态机表达：persistent 变量作为**跨会话初始状态的守卫**
- Ren'Py 实现：进 label 写 `$ persistent.seen_route_a = True`；引擎 `renpy.seen_label()` / `renpy.seen_image()` 内置"是否看过"查询
- 与普通多周目 flag 的关系：剧情锁是其中专门用于"经历记录"的一类（进过分支/看过 label → 解锁）

### 1.6 不确定性处理（确定性分级）

> 识别叙事描述时，遇到"都可能"的不确定处（Q13/Q14 场景）——**标记为"待确认"，不擅自假设**。

- 默认路线去向不明 → 标记 `pending: 默认路线去向待确认`
- 分支后是否汇聚不明 → 标记 `pending: 汇聚关系待确认`
- 随机概率数值缺失 → 标记 `pending: 概率待确认`
- **原则**：能确定直接转，不能确定标记待确认，不臆测

### 1.7 插值与分叉的界定（协作确认）

> **高频变量插值不作为分叉判定依据，而是追踪变量本身。**

- **不做**：用文本相似度判断是否分叉（插值 `[affection]` 等会污染判定）
- **做**：追踪插值背后的**变量流**——变量在哪写、哪读、如何随路线变化
- **结构分叉靠转移/守卫判定**（from/to/guard）；**内容差异靠变量追踪**（不是文本）
- **文本是渲染层**，不作为状态划分依据

**变量追踪粒度（视用途）**：
| 用途 | 粒度 |
|---|---|
| 设计文档（轻量） | 读写位置 + 值域 |
| 代码分析（重量） | 完整变量流（初始→最终的变化路径） |

### 1.8 人机协作边界（协作确认）

> 识别有歧义时——**不猜，标记待确认并直接询问用户**。

- 能确定 → 直接转状态机
- 有歧义（如"选择影响对话"难界定是否分叉）→ **标记待确认 + 询问用户**

### 1.9 路线上下文与路线的建模（协作确认）

**路线上下文的表达因游戏结构而异**：
- **分支早且不交叉**的游戏：几乎只会是**隐式**（读者知道当前在哪条线，不写"在X线中"）
- 分支晚 / 交叉多：可能显式前缀（"在救人线中..."），也可能仍隐式

**识别原则**：
- 识别"路线上下文"**不能依赖显式前缀**——大多数情况隐式（靠已建立的路线状态推断当前上下文）
- 显式前缀是**加强信号**，缺失不等于没有上下文
- **维护"当前路线上下文"为隐式状态**，显式提及是重申/切换
- 隐式上下文 = 状态机的"当前状态"本身携带路线信息（在哪个状态 = 在哪条线）

**路线的建模（route-map.json）**：
- 状态带 `route` 标记（属于哪条线）
- 路线**不做独立概念层**（无 routes 数组），从状态分区推断
- 分支早且不交叉的游戏：路线 ≈ 状态集合的分区

## 二、叙事描述 → 状态机要素识别

> 核心职责：从**任意叙事描述**中识别状态机要素（状态/转移/守卫/事件），不依赖单一格式。
> 主要教 AI 识别"叙事描述中的状态机要素"，而非定义唯一标准格式。

### 2.1 信号词识别表（作者确认的措辞）

**分支/条件类**：
| 叙事措辞（真实用法） | 状态机要素 |
|---|---|
| "如果某个数值满足某个条件，就..." | 守卫 → 转移 |
| "如果...进某路线" | 守卫 → 状态（路线） |
| "在某路线中，这个事件不发生" | 路线守卫抑制转移（上下文相关，常隐式） |
| "在某路线中，只有这个分支" | 路线内出转移受限 |
| "要达成某结局，需要满足..." | 结局状态的前置守卫 |
| "选择只影响后面几句对话" | 变量追踪（不假定分叉，见 1.7） |
| "从这里到这里进入循环，需要XX操作才能出来" | 带脱出条件循环 |
| "剧情锁" | persistent 跨存档守卫 |
| 概率描述（"30% 触发""随机遇到"） | 随机转移（guard + probability，见 1.5） |

**时间/顺序类**：
| 叙事措辞 | 状态机要素 |
|---|---|
| "先...再..." | 顺序转移（sequential） |
| "直到...才..." | 守卫（until 条件满足才转移） |
| "之后" / "接下来" / "然后" | 顺序转移 |
| "在此之前" / "在那之前" | 时序约束（前置状态） |

**状态/上下文类**：
| 叙事措辞 | 状态机要素 |
|---|---|
| "此时" / "这时候" / "当前" | 状态描述（当前执行位置） |
| "在X线中" / "这条线里" | 路线上下文（显式重申，常隐式） |

**触发/解锁类**：
| 叙事措辞 | 状态机要素 |
|---|---|
| "触发" / "开启" / "激活" | 事件触发的转移 |
| "解锁" | 守卫满足后可用（剧情锁/flag） |
| "条件满足后" | 守卫 → 转移 |

### 2.2 识别步骤

1. **扫分支点信号**："选择/分支/如果/选项/要不要/这里可以"等
2. **识别默认路线**（Q10：没触发条件时一直存在的路，常隐式）
3. **逐条识别条件分支**（"如果X"→守卫，"进入Y"→目标状态）
4. **识别数值阈值**（"好感达到70"→ affection >= 70）
5. **识别路线上下文**（隐式为主，显式为加强）
6. **识别时序**（先/直到/之后 → 顺序与守卫）
7. **标记待确认项**（歧义处，见 1.6/1.8）

> 注：信号词是**识别线索**而非硬规则——AI 应结合上下文理解措辞变体，信号词帮助定位候选要素，最终以状态机一致性为准。

## 三、状态机 → Ren'Py 代码映射

> 核心职责：把状态机（状态/转移/守卫/事件）翻译成 Ren'Py 代码框架（设计文档→代码方向）。

### 3.1 状态划分粒度（作者确认）

**看情况**：交互点=状态用 label；纯顺序流程可合并。
- 一个状态 = 一个 label（交互点/分支点/menu）
- 纯顺序流程（无交互无分支）可合并进相邻状态
- 生成代码时，交互点/分支点独立 label，顺序段内联

### 3.2 转移类型 → 代码映射

| 状态机转移 | Ren'Py 代码 |
|---|---|
| sequential（顺序） | 直接写下一语句（内联） |
| jump | `jump <label>` |
| call / return | `call <label>` / `return` |
| menu（事件 choice） | `menu:` + `"选项":` + jump/call |
| conditional（if 守卫） | `if 条件:` + jump（+ `elif`/`else:` + jump） |
| **switch/match（多路离散）** | Python `match 变量:` + `case "值":`（或 if/elif 链） |
| conditional（数值范围） | `if 变量 >= N:` 链（if/elif 适合范围判断） |
| conditional（随机） | `if renpy.random.random() < p:` 分支 |

### 3.3 switch 与 if/elif 的选择（作者确认）

- **离散值枚举**（route == "a"/"b"/"c"）→ `match` 语句（Python 3.10+，Ren'Py 8.5 支持）
- **数值范围判断**（affection >= 70）→ if/elif 链
- 两者在**状态机上同构**（都是 conditional 转移集合，guard = 值/范围判断）
- **不独立成转移类型**——归入 conditional，代码生成时按"离散/范围"选择 match 或 if/elif

### 3.4 状态 → 代码生成规则

| 状态机元素 | .rpy 代码 |
|---|---|
| 状态 s（name, entryActions） | `label <name>:` + `$ var = val`（entryActions） |
| 守卫变量 | 由变量的 default/define 生成 `default` 声明 |
| ending 状态 | `return` 或场景结束 |
| 剧情锁（persistent） | `$ persistent.seen_x = True`（进入时写） |

### 3.5 生成骨架示例

```
状态机：
  [start] --default--> [prologue]  (entryActions: route=start)
  [prologue] --menu choice:"救她"--> [rescue_line]
  [rescue_line] --guard: affection>=70--> [true_end]
生成：
label start:
    $ route = "start"
    jump prologue
label prologue:
    $ route = "prologue"
    "序章……"
    menu:
        "救她":
            jump rescue_line
label rescue_line:
    $ route = "rescue_line"
    if affection >= 70:
        jump true_end
    else:
        jump rescue_line   # 示意：此处应有数值增长逻辑（如 $ affection += 5），循环带脱出条件
label true_end:
    return
```

## 四、Ren'Py 代码 → 状态机提取

> 核心职责：静态分析 .rpy，提取状态机（代码→设计文档/路线地图方向）。
> 已有工具：分析器 `verification/scripts/extract-route-map.js` + 生成器 `verification/scripts/generate-route-code.js`（双向闭环），本章为 skill 知识规范。

### 4.1 提取规则

| .rpy 语法 | 状态机元素 |
|---|---|
| `label x:` | 状态（kind=label，记录真实行号） |
| `jump x` / `call x` | 转移（type=jump/call） |
| `return` | 转移（type=return，无目标） |
| `menu:` + `"选项":` + jump | menu 状态 + 选项转移（event=choice） |
| `if/elif/else:` + 块内 jump | conditional 转移（guard=条件，true/false 分支） |
| `match 变量:` + `case` | conditional 转移集合（离散值守卫，同构于 if/elif） |
| `$ var = val` | entryActions + 变量写入 |
| `default/define var` | 变量定义（label 外也须提取） |
| say / 字符串插值 `[var]` | 交互点 + 变量读取 |
| `renpy.random` | 随机转移（probability 推断） |
| `persistent.x` | 剧情锁/跨存档变量 |
| 注释（`# 路线/分支/条件说明`） | 辅助线索（见 4.2） |

### 4.2 注释的角色（作者确认）

**辅助线索**：有则参考，无则靠代码结构推断。
- 注释是设计者意图的补充信号（`# 分支点：好感达标进真结局`）
- **不依赖**：不保证有、不保证准——提取以代码结构为准
- 注释可用于：标注 pending 确认项、补充状态描述、推断设计意图

### 4.3 提取注意事项

1. **label 真实行号**：被 jump 先引用补建的状态，遇到真实 `label x:` 定义时更新行号
2. **if/elif/else 链完整处理**：每个分支一条 conditional 转移，else 分支 guard=else
3. **嵌套 label**：label 内嵌套 label（循环体）是独立状态，父状态与子状态的顺序流转需识别
4. **缩进敏感**：menu/if 块内跳转在更深缩进，按缩进边界解析；同缩进的多个 if 块是顺序关系（不可跳过）
5. **守卫变量记录**：guard 表达式里的变量应计入 readIn
6. **死路/循环两阶段判定**：①结构（有无出转移）②守卫可满足性（带隐含脱出条件的是合法循环）
7. **去重**：同 from/to/type/label 的转移去重；conditional 与纯 jump 并存时保留 conditional

### 4.4 提取产出

route-map.json（状态机结构）：
- states：label/行号/entryActions/outTransitions
- transitions：from/to/type/guard/event/choiceText
- variables：读写位置 + 值域 + 守卫引用
- meta：endStates/deadStates/loops/unresolvedLabels

## 五、设计规范与调试衔接

### 5.1 分支设计规范（L2 通用原则）

1. **每个分支点必须有明确的可达出口**（不留彻底死路）
2. **循环必须有脱出条件**（带隐含脱出条件的循环是手法，彻底循环是缺陷）
3. **分支后的汇聚点要清晰**（如果要汇聚——汇聚是中间节点，可再分叉）
4. **变量命名策略**：语义化 + **简写编号分组**（变量过多时采取 `flag_01`/`route_a`/`aff_1` 等短名+编号分组管理，平衡可读性与简洁）
5. **数值阈值管理**：好感度/概率等阈值集中定义（常量/define），不散落魔法数
6. **关键分支点加注释**（辅助提取与维护，见 4.2）

### 5.2 状态机驱动的调试能力

> 状态机结构天然支撑调试（详见 .research/05-调试器技术规划.md）。

| 调试能力 | 机制 |
|---|---|
| warp 定位到状态 | 状态有 file:line → `--warp` / `renpy.warp_to_line()` |
| 强行跳转 | `renpy.jump(label)` + entryActions 变量注入 |
| **变量运行时注入改动** | `renpy.store.x = val`（运行时改变量，调试分支条件） |
| 变量监测 | 快照 diff + 变化报告 |
| **随机数查看范围/条件** | 调试时显示随机转移的 probability 与条件 |
| **随机数锁定** | 注入 seed / 强制覆盖 random 值 → 稳定复现特定概率分支，检查功能 |
| 路线图可视化 | states/transitions 渲染成可点击图，点状态跳转 |
